# fastIPAV 実機受入試験

この文書は CI の代わりではない。CI は synthetic な GStreamer 入力と loopback RTP を検証するが、実キャプチャ・実画面・実ネットワークの性能を保証しない。実機の結果を日付、機器型番、OS、GStreamer 版、設定ファイルのハッシュと共に記録する。

## 試験環境を記録する

- TX/RX 各マシンの OS、CPU/Raspberry Pi 世代、メモリー、接続方式、有線 NIC、MTU、ディスプレイを記録する。
- UVC/HDMI capture のメーカー・型番・入力解像度・フレームレート、音声インターフェース名を記録する。
- `uname -a`、`gst-inspect-1.0 --version`、`ip -br addr`、`ip -br link` の出力を保存する。
- TXで `v4l2-ctl --device /dev/video0 --list-formats-ext` を実行し、設定した `video.source_caps` をデバイスが実際に提供することを確認する。
- RXで `gst-inspect-1.0 kmssink` または表示環境に適した sink を確認する。Pi 5 は H.264 のハードウェアコーデックを前提にしない。
- 利用するインターフェースが複数ある場合は `network.interface` を明示する。

## 構成検査と基本動作

以下はデフォルトの HTTP ポートを使う例。必要なら実際の設定に合わせる。

1. TX/RX で `--check-config` を実行する。これは GStreamer のパイプライン解析であり、カメラ・ディスプレイ・音声デバイスが実際に動作することの証明にはならない。
2. TX を起動し、別ホストの RX を起動する。システムサービスの場合は `systemctl status avoverip-tx` / `systemctl status avoverip-rx` と `journalctl -u avoverip-tx -n 100` / `journalctl -u avoverip-rx -n 100` を参照する。
3. **TX のホストで** `curl -i http://127.0.0.1:8081/healthz`、**RX のホストで** `curl -i http://127.0.0.1:8082/healthz` を確認する。入力開始前は 503、メディアを検出した後は 200 と `"ok":true` が期待値。
4. TX/RX 各ホストで `curl -fsS http://127.0.0.1:8081/stats` / `curl -fsS http://127.0.0.1:8082/stats` を採取する。`frames_total` が継続的に増えることを確認する。音声を使う場合は両端の `audio_chunks_total` も増えることを確認する。
5. RX の**物理画面上**で映像の描画、映像の欠落・乱れの有無を観察する。バッファカウンターの増加だけでは表示成功を証明できない。
6. TX の送信、RX の受信がそれぞれ video-only と video+audio の設定で意図どおり動作することを確認する。音声利用時は左右チャンネル・音量・ノイズ・途切れを実際に聴取する。

## 低遅延ソフトウェアデコーダーのA/B計測

- 同一TX・同一1080p30入力・同一ディスプレイ・同一ネットワークで、RXの`decoder_element = "avdec_h264"`（比較基準）と`decoder_element = "avdec_h264 thread-type=slice"`（低遅延候補）を交互に測る。RTP jitter latencyは双方とも現行設定から変更しない。
- 正確なcapture-to-display遅延は、入力映像と表示映像の両方が写る高速度撮影やフレーム番号入り映像などで比較する。`/stats`の`estimated_capture_to_display_ms`は実測値ではないため代用しない。
- 少なくともウォームアップ後の各100フレーム以上を観測し、中央値とp95、欠落・重複フレーム数を記録する。熱的な定常状態、入力FPS、NIC経路、時刻同期などを同一条件に保つ。
- 両構成でRXの`frames_total`増加、`pipeline_restarts`、QoS、CPU/温度、画面の滑らかさを記録する。sliceが遅延を減らしても1080p30を維持できない、あるいはフレーム落ちが明確に増えるなら既存設定に戻す。
- GStreamerのローカル要素遅延を調べるときは`GST_TRACERS='latency(flags=pipeline+element+reported)'`と`GST_DEBUG='GST_TRACER:7'`をRX起動時に指定する。これは画面に実際に表示されるまでの時間を保証しない。
- 古いインストール済みの`/etc/avoverip/rx.toml`はアップグレード時に上書きされない。新設定を試す場合はそのファイルの`decoder_element`を書き換え、RXサービスの再起動が必要。

## 安定性と障害復旧

- 目標解像度（例: 1920x1080 / 30fps）で連続運用し、CPU使用率、温度、メモリー、画面描画の安定性、再起動回数を時系列に記録する。計測期間と合否基準は試験開始前に決める（例: 4時間、予期しないプロセス終了ゼロ）。
- TX 停止中の RX は 503 で待機でき、接続済みのストリーム喪失後は検知・再起動・TX 復帰後の受信再開に成功することを確認する。
- TX を再起動し、再起動後の RX 側の自動復帰、映像の表示復帰までにかかった時間をストップウォッチなどで記録する。
- 有線接続の切断・再接続を安全な試験用ネットワークで実施する。複数NICの切替とIPv4 MTUの不一致についてはエラーの診断が妥当か確認する。運用中のネットワークへ無断でパケット損失を注入しない。
- パケット損失・ジッター試験は隔離した試験環境で行う。RTP は再送や FEC を備えないため、失われた映像が完全に回復することを合格条件にしない。復帰までの時間、映像破損の程度、音声断続を記録する。
- systemd の再起動とOSの再起動後に、期待するサービスだけが有効になり、必要なデバイスにアクセスできることを確認する。
- 既存設定を保持したアップグレード、互換性エラーによる事前拒否、およびインストール途中の失敗時の旧バイナリへの復元をテストする。更新失敗時の**共有アセットやsystemd設定の完全ロールバックは未実装**である。

## 判定時の注意

- `/healthz` は各ホスト内のパイプライン監視であり、受信側の映像を人間が実際に見られた証明にはならない。
- `estimated_capture_to_display_ms` は実測未実装で `null`。RTPジッターバッファの設定値からエンドツーエンド遅延を確定しない。
- `estimated_av_sync_ms` と `estimated_audio_offset_ms` は設定値由来の推定で、唇・音声の真の同期誤差ではない。映像と音声は独立した RTP ストリームであり、RTCP による送信クロック同期は未実装。
- `dropped_frames` と `dropped_audio_chunks` は検出できた警告由来であり、精密なパケット損失率ではない。
- 複数送信元は multicast group/port を別にする。受信側は送信元 SSRC を選別しない。
